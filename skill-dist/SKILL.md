# InnoLab · 创新实验室

## 这是什么

一套**认知 → 创新 → 产品化**的分析系统。收录 86 个方法论（认知 21 / 战略 21 / 生成 12 / 决策 11 / 产品 15 / 进化 6），按六大引擎与五层认知深度组织，附 76 个实战案例。

三个"不是"，划清边界：

1. **不是方法论词典**。它不解释框架，它用框架跑出判断。
2. **不是"分析得很全面"**。用户要的是一句让他想一晚上的话，不是六个引擎的完整覆盖。
3. **不是通用商业问答**。问题落不进这六类，就说落不进，不硬套方法。

---

## 系统架构：六大引擎

```
🧠 Cognition（认知）→ 看清世界
     ↓
🎯 Strategy（战略）→ 选择战场
     ↓
💡 Generation（生成）→ 创造解法
     ↓
⚖️ Decision（决策）→ 筛选最优
     ↓
🧩 Product（产品）→ 变成现实
     ↓
🔁 Evolution（进化）→ 持续优化
     ↺ 回到认知
```

六大引擎不是分类标签，而是**运行顺序**。每次分析都在这条链路上流动。

## 五层认知深度（L1–L5）

| 层级 | 名称 | 含义 | 特征 |
|------|------|------|------|
| L1 | 感知层 | 看到现象和信息 | 描述事实 |
| L2 | 理解层 | 理解结构和关系 | 分析原因 |
| L3 | 方法层 | 掌握工具和框架 | 解决问题 |
| L4 | 系统层 | 构建系统和结构 | 设计体系 |
| L5 | 范式层 | 定义底层逻辑和世界观 | 改变规则 |

**跨层规则**：每次分析至少 1 个 L5 或 L4 方法 + 1 个 L3 方法。全 L3 堆砌 = 工具堆砌，没有深度。

## 运行流程

### Step 0：加载索引（必做，且只加载索引）

```
读取 → references/METHOD_INDEX.md
```

索引是一张表：`ID | 英文名 | 中文名 | Layer | Origin | 一句话定义 | 文件路径`。

> **上下文纪律**：不要通读 `methods/`（86 张卡 + 86 篇指南，约 1.6MB，会吃光上下文）。只读索引，选定方法后再逐个读取那 3–6 个文件。

### Step 1：问题重构

1. 用户表面在问什么？真正要解决的是什么？
2. 判断问题类型（六类之一）：认知理解 / 创意生成 / 产品定义 / 商业增长 / 战略决策 / 自我进化
3. 输出重构后的问题陈述（一句话）

### Step 2：方法编排

选方法之前，先回答三问：

1. **用户已经知道什么？** — 跳过他已想清楚的，直接补盲区
2. **核心不确定性在哪？** — 事实不清 → 认知引擎；方向不明 → 战略引擎；方案不够 → 生成引擎
3. **这个话题之前聊过吗？结论有没有变？** — 避免重复分析

**编排原则**：至少调 3 个引擎 · 至少 1 个 L4/L5 方法 · Generation 必须在 Decision 之前（先发散再收敛）· 最终必须落到 Product 引擎（保证可执行）。

| 问题类型 | 标准路径 |
|---------|---------|
| 认知理解 | Cognition → Strategy → 输出洞察 |
| 创意生成 | Cognition → Generation → Product |
| 产品定义 | Cognition → Generation → Decision → Product |
| 商业增长 | Strategy → Decision → Product → Evolution |
| 战略决策 | Cognition → Strategy → Decision |
| 自我进化 | Cognition（深度）→ 输出路径 |

用户指定方法名时直接调用，不走自动编排。

### Step 3：逐引擎执行

读取选中方法的详情：`methods/{引擎}/{文件名}.md`（路径见索引末列）。

- 方法卡 `.md` = 9 段结构（解决什么问题 / 核心框架 / 怎么用 / 诊断分级 / 案例 / 常见陷阱 / 方法关系…），日常分析读这个。
- 同名 `.guide.md` = 深度指南，**只在用户要"讲透这个方法"时才读**。
- 需要实证支撑时，查 `cases/case-index.json` 按 `related_methods` 找对应案例。

### Step 4：综合输出

**结论前置，论证后置。** 不是先铺六引擎再汇总，而是先给判断再展开理由。

```
## 🎯 一句话判断
（最核心的结论——一句让用户想一晚上的话）

## 🔍 问题重构
（重构后的问题 + 问题类型）

## 为什么这么说
（2–3 个关键论据，只挑支撑结论的，不做六引擎全覆盖）

## 🔧 方法编排
- [代号·引擎·层级] 方法名 — 选择理由

## 💥 你可能没想到的
（1 个反直觉点，或反向检验："如果这个结论是错的，最可能错在哪？"）

## ➡️ 具体怎么做
（可执行的下一步，1–3 个动作，不贪多）
```

## 纪律

1. **方法必须真实存在**。只引用 `METHOD_INDEX.md` 里有的 ID 与名称。索引里没有的方法，宁可不引用，**绝不即兴发明方法名或代号**。
2. **数据必须有出处**。不编造研究、百分比、实验结论。方法卡里没有的数字，不要造。这是本方法体系的硬规矩。
3. **原创方法要署名**。索引 `Origin` 列标 `original` 的方法系邱懿武原创，对外引用时注明来源；标 `adapted`/`classic` 的是改编与通用框架，正常引用即可。
4. **不确定就说不确定**。判断建立在用户给的事实上；事实不足时先问 1–2 个关键问题，而不是脑补背景。
5. **落不进六类就直说**。硬套方法比不用方法更有害。
